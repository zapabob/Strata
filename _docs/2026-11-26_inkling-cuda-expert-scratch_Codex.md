# Inkling CUDA Expert scratch storage

The change targets one RTX 5060 Ti with 16 GiB VRAM, a Ryzen 5 4500 with six physical cores, and 32 GiB system RAM. The two inputs are the checksum-verified SC117 SQ-10 pack and the Heretic Mode B NVFP4 GGUF. The experiment uses the same native Strata binary, token IDs, decoding settings and Expert budgets for both. GPQA has 198 fixed prompts and Apex has 12, with 8,192 generated tokens allowed for each Apex prompt. The evidence lives with the local model card.

`--expert-cache-dir` lets the native CUDA loader use an existing temporary directory on NVMe or SATA. The loader places overflow Experts into sector-aligned scratch storage and serves them through the existing bounded cold-reader ring. The original weight files are read-only. On Windows, the file is delete-on-close and the allocator and cold reader share delete access. Shutdown closes the cold reader before releasing the writer. On POSIX, the opened file is unlinked after the reader attaches. The scratch admission check retains a 5 GiB volume reserve. The runtime reports actual SSD bytes and I/O errors.

`--expert-cache-min-mib` supports a controlled test with a small nonzero SSD tier while granting the host a larger RAM budget. The offload profile streams the SQ-10 trunk in 16 MiB pieces, consumes the assembled GGUF trunk, and reserves its working area before populating it. It stages one Expert body at a time for weights already in a native representation. The conversion path for other GGUF representations retains its layer-wise processing. A single CUDA GPU is required for the scratch path.

The comparison retains the Strata recurrent graph and its native Blackwell Expert kernels. The local llama.cpp reference and Strata both use the `m16n8k64` block-scaled NVFP4 MMA on supported paths. Strata already has a bit-exact NVFP4-to-SF4 Expert adapter. The initial profiling therefore focuses on Expert placement, I/O and activation batch size. See the [llama.cpp licence](https://github.com/ggml-org/llama.cpp/blob/master/LICENSE) and [CUDA quantised matmul](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cuda/mmq.cu).

The CUDA 13.5.37 build uses CMake and Ninja under Visual Studio 2022 with five compiler jobs. The C++ test `inkling_expert_spool_test` read exact bytes through the cold scheduler and verified scratch cleanup on both the C: NVMe volume and the H: SATA SSD. The H: test directory was empty when its inherited NTFS compression flag was cleared. A CUDA 13.3 diagnostic ran concurrently with a build and stopped at the existing physical-memory floor, before throughput measurement. All 50 Python regressions passed during the CUDA 13.5 work.

On C:, the first SQ-10 profile achieved 16.82 prefill tokens/s and 3.35 decode tokens/s. A tuned profile with 6.5 GiB for GPU Experts, up to 5 GiB for host Experts, a 256 MiB minimum SSD tier and a 128-token chunk achieved 264.52 prefill tokens/s and 13.76 decode tokens/s for SQ-10. Both rates are medians of three uncached 512-input, 128-output trials. The combination of placement, batch size and runtime lane changed together. The 16-token smoke sequence matched between the two SQ-10 profiles. NVFP4 produced visible text with the same tuned settings and about 345 MB of SSD reads during its 16-token request. Its next request encountered the 3 GiB available-RAM floor and stopped when the reading reached 2.89 GiB. The temporary Expert file was removed on both exits.

GPQA uses one native greedy choice among the four raw letter tokens A, B, C and D. The runtime scores these choices against the full logit row with ties resolved by token ID. Apex uses unconstrained greedy generation and the frozen official grader. A Windows OpenSSL exception in the grader dependency import was resolved by clearing the inherited TLS key logging variable in the benchmark process. The positive and negative boxed-answer controls passed. See the [CPython issue](https://github.com/python/cpython/issues/152784).
