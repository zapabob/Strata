## Ordered work

1. **Measure the baseline and label every fixture.** Freeze the model, engine runtime, context capacity, actual prompt length, sampler and output token count. Record short-context cold/warm traces with SSD logical and physical bytes, real cache hit bytes and exposed stalls. Run an instrumented bridge for each routing format in use. Capture prefill and decode separately. Obtain the dense BF16 capacity result with a supported CPU+CUDA file-mapped path. Its 50.11 GiB text file is larger than the approximately 47.80 GiB combined installed VRAM and RAM.
2. **Replay and search only effective knobs.** Compare LRU, LFU, layer/Zipf, Markov, the existing heuristic, uniform random search and the offline oracle under the same resident byte budget. Split recordings by workload and session into optimisation and never-seen holdout data. Start with RAM/VRAM tier capacities, I/O chunking, prefetch depth, confidence threshold, queue limits, CPU affinity and eviction hysteresis where the engine exposes them. Compare official ShinkaEvolve to the existing simulator at the same evaluation and time cost. Only use model-generated algorithms or kernels after the settings interface and independent verifier are stable.
3. **Schedule data at the deadline.** For request \(e\), the exposed stall is \(\max(0,t_{\rm queue}+t_{\rm read}+t_{\rm stage}+t_{\rm PCIe}-t_{\rm lead})\). Use demand-first service, bounded pinned staging, coalesced reads, events and multiple buffers where the timing demonstrates overlap. Estimate justified cache priority from expected avoided stall per byte. Maintain a cold path for unpredictable expert activation and measure unused work after speculative prefetch. For dense models, test layer placement, weight reuse and multi-token verification under the same numerical reference. Report single-sequence latency and batch throughput independently.
4. **Optimise the measured CPU or GPU bottleneck.** Reuse the AVX2 expert path and identify load, PCIe and GPU launch overlap on this six-core topology. Candidate CUDA targets include GEMV/GEMM, dequantisation, GDN, attention, RMSNorm and graph scheduling. Use same-build reference tensors, a bounded search for legal tile and fusion settings, separate holdout shapes and seeds, wide value ranges, non-aligned and boundary cases, and CUDA memcheck/racecheck/synccheck where supported. An independent process owns reference code, tolerances, output validation and synchronised timing. Candidate generation has no write access to those inputs.
5. **Test compression and verify useful work.** Test shared bases \(W_e=W_{\rm shared}+U_eV_e^\top+E_e\) against the original weighted error and include scales, residuals and reconstruction traffic. Adopt a candidate only after conditional state error, full-vocabulary KL where available, top-1 agreement, resource safety and held-out task performance pass. Compare matched Hadamard/SO(8), Spin(8) vector, mixed-precision and NVFP4 variants individually. Compare verified successes per total wall time with cumulative optimisation and verification budgets. Record failure, abstention and censoring. [CIK theorem and proof conditions](../research/nkat-urt-cik/THEOREMS.md).

## Performance constraints and acceptance

For average measured device traffic \(W_{\rm SSD}\) per emitted token, effective bandwidth \(B_{\rm SSD}\) alone bounds throughput by \(B_{\rm SSD}/W_{\rm SSD}\). With MoE active bytes \(W_a\), a byte hit rate \(h\), and demand reads only, the ideal demand volume is \((1-h)W_a\). Add alignment, coalescing amplification, wasted prefetch and repeated reads to obtain physical volume. For dense execution, accessing every layer on each pass makes the unavailable working set the first cost estimate. Use measured physical bytes, because file-cache behaviour and storage compression can change device traffic. Verified multi-token processing can amortise reads across accepted tokens. Check end-to-end output quality and accounting before claiming a speed improvement.

The multi-resource bound is the minimum of available compute rate per operation count and bandwidth per byte count for each active GPU, CPU, RAM, PCIe and SSD resource. Compare that bound with the actual critical path. In particular, the 30 tok/s exploration target is a hypothesis. The 4K Q38 fit-case gives evidence for quantised inference, and the BF16 capacity exercise has its own performance gate.

Evaluate in ascending cost from static invariants, CPU replay and cost model, through CUDA microbenchmarks and fixed-token hardware tests, to long-context and held-out TSI tasks. Promote a small sample of lower-ranked candidates to estimate how often the proxy misses a useful candidate. Track paired baseline-versus-candidate timing blocks and keep the final test data frozen. For acceptance use a prespecified lower confidence bound on measured improvement and account for adaptive comparisons. A Hoeffding formula requires independent, bounded observations and a justified range. Otherwise use a paired procedure with its actual assumptions. Record the search hours and break-even token count using measured time saved per token plus build and validation cost.

The first diagnostic compared F16 KV with Spin(8) K8V4. Its lower KV payload came with a 31/33 logit argmax match and higher end-to-end diagnostic time. The cap-three MTP trial failed its fixed-token parity and speed comparisons. Keep these results in the archive. Capture peak RAM and VRAM, per-device SSD read bytes, deadline misses, PCIe transfer time, time to first token, emitted-token counts, test-specific quality, and search and verification costs. Use null for data an instrument could not obtain. [Fixed-token evidence](../research/nkat-urt-cik/evidence/q38-kv-pair.json).
